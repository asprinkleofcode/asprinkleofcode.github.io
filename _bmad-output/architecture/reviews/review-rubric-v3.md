## Findings

| # | Sev | Checklist | Finding | Suggested close |
| --- | --- | --- | --- | --- |
| **C-1** | high | 1, 3, 5, 7 | **AD-20 doesn't say where the care guide's `pdf` field lives, and AD-2's still-standing text answers a different question than AD-20 does.** AD-2 (unchanged by this update) says: *"A `personal` entry with `listed: false` is reachable at its route but never appears in the `/beyond` index or a teaser: that is how a **supporting** page (**the care guide**) exists without becoming a third Beyond the Code dimension."* That sentence describes the care guide as its **own separate `personal` .mdx file** — its own registry entry, its own `/beyond/:slug` route (per AD-5, every personal file gets one), just hidden from the index via `listed:false`. AD-20 describes a materially different mechanism: an optional `pdf?: string` field added to "`personal` frontmatter" generically, with no statement of *whose* frontmatter it lives on. Two structurally different, equally-literal readings survive: (a) the field sits on the **existing Birdhouses entry's own frontmatter** — no new file, no new route, the Birdhouses detail page itself renders a download/view affordance (this matches PRD A-12's "surfaced from the Birdhouses dimension" most directly, and makes AD-2's `listed:false` example simply wrong/obsolete); or (b) the care guide is still **its own separate hidden `personal` entry** (per AD-2's example) that happens to also carry a `pdf` field, reached by a whitelisted in-body link from the Birdhouses story (per AD-8) — in which case AD-20 should say so and AD-2's example still holds, but nothing in AD-20 confirms this reading either. Builder A ships (a); builder B ships (b); both cite a real AD sentence for their choice. This is exactly the "Deferred item silently creates the third dimension AD-18/D-18 forbid" risk a prior gate pass (v2, H-4) already flagged once against the *old* Deferred framing — AD-20 was supposed to close that risk and instead re-opens the same fork one level down, now against AD-2 instead of against a Deferred row. Corroborating evidence that the ambiguity is inherited, not invented by this review: EXPERIENCE.md v0.8 §9.3 and its "Birdhouse Flow" diagram are themselves stale on this exact point — both still say the care guide is "assumed to be a lightweight page within the portfolio, an external link acceptable if one exists" (the pre-A-12-resolution framing), never updated to A-12's actual resolution wording. AD-20 correctly follows the *resolved* PRD A-12 over EXPERIENCE's stale §9.3, but never explicitly reconciles the routing/registry consequence against AD-2. | Pick one and say so in AD-20 (or amend AD-2's example): recommended — the `pdf` field lives on the **Birdhouses entry's own frontmatter** (matches "surfaced from the Birdhouses dimension" most literally and needs no new route); then strike or rewrite AD-2's `listed:false` care-guide example, since it would no longer be true, and either give `listed` a different illustrative use-case or note it currently has none in the shipped MVP content set. If (b) is actually intended instead, AD-20 must say explicitly that the care guide is a second, hidden `personal` entry linked from within the Birdhouses story body, and AD-2's example stays valid as-is — either way, one AD must name the shape, not both leave it open. |
| **M-1** | med | 2, 5, 7 | **`--header-height` is not stated to be responsive, and the header's actual height is not yet fixed anywhere.** AD-19's Rule reads: "one shared `--header-height` custom property, set where the header is sized, drives `scroll-padding-top`... and `scroll-margin-top`..." This assumes a single stable value, but EXPERIENCE §5.2 also specifies a mobile hamburger collapse (`NavbarToggle`/`NavbarCollapse`) that changes the header's rendered footprint at the mobile breakpoint (and potentially further while the collapsed menu is open). If `--header-height` is authored as one static value sized off the desktop row, mobile anchor/heading offsets under- or over-compensate; if two builders each guess differently (one hardcodes per-breakpoint overrides, another leaves it static and eats the drift), that is exactly the per-page-offset divergence AD-19 exists to prevent, just relocated to per-breakpoint. The AD is silent on whether the token is breakpoint-aware, and on whether it must reflect the *collapsed* (default) header state only or also the *expanded* mobile-menu state. | One clause: `--header-height` reflects the collapsed/default header height only (the expanded mobile dropdown is a transient overlay, not part of the scroll-offset contract), and it is redefined at whatever breakpoint(s) the header's own layout changes — still one variable, one owner (the Header component/CSS), never computed per-consumer. |
| **L-1** | low | 2 | **AD-20's `<iframe>`/`<object>` embed path isn't cross-referenced against AD-15's semantic/accessibility baseline.** AD-15 requires "meaningful link text" and implicitly an accessible baseline for all embedded content, but neither AD-15 nor AD-20 states that the in-page PDF preview needs a `title` attribute on the `<iframe>` (or accessible fallback content on `<object>`) — an easy, invisible-until-audited omission a builder could ship without violating either AD's literal text. | Add one sentence to AD-20 (or AD-15's binds list) requiring an accessible name on the embed and fallback content/link for browsers that don't render the embed inline. |
| **I-1** | info | — | **Not a spine defect, flagged for the gate owner:** `EXPERIENCE.md` v0.8 §9.3 ("Making / Birdhouses") and its "Birdhouse Flow" diagram, and `SPEC.md`'s §14.3 open-question list, all still describe the care guide as "a lightweight page within the portfolio, an external link acceptable if one exists" — the pre-resolution assumption from PRD A-12 before its 2026-09-12 owner decision ("a downloadable PDF document... surfaced from the Birdhouses dimension"). This staleness is very likely the root cause of C-1: the spine's own AD-20 correctly tracks the *resolved* PRD A-12, but the UX document it's supposed to be consistent with hasn't caught up, so there was no EXPERIENCE-level statement of registry shape for AD-20 to ratify against. Same pattern as the v2 gate's I-1 (`SPEC.md` citing a stale EXPERIENCE version) — out of this lens's edit scope, but worth a companion-doc sync pass. | Out of spine-editing scope; recommend an EXPERIENCE/SPEC touch-up pass reflecting A-12's resolution before the care-guide story is scheduled. |
