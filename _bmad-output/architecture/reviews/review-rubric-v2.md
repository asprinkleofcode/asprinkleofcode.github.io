| **H-1** | high | 1, 2 | **AD-18 and AD-2 give opposite answers for a zero-story path index.** AD-18: "No route, nav entry, **path card**, or teaser slot may be conditional on content that does not exist." AD-2: "Index, teaser, and **path surfaces render only from real registry entries** — no empty-state shells." With zero Engineering stories in the registry, builder A shows the Engineering card linking to an index that renders nothing (an empty shell — violates AD-2/NFR-4), builder B hides the card until a story exists (violates AD-18), builder C renders "No stories yet" (violates the no-placeholder floor, D-12). This is not hypothetical: AD-17 sequences the toolchain story first and explicitly allows path-surface work to precede story content, so the zero-content state is a real shipped state. EXPERIENCE §14 does not resolve it — it says "gracefully omit or simplify" for *optional* content, and a fixed D-15 path is not optional. | AD-18 (or AD-2) names the legal zero-content render for a fixed path: the three path entries are structural and always present; a path index with no registry entries renders its path framing (heading + what the path represents, per CAP-3 intent) and no card region at all — no cards, no shell, no "coming soon". |
| **H-2** | high | 1, 5 | **The semantic-token layer has no owning story, and AD-10 is unbuildable until it exists.** Today `src/theme/colors.css` contains *only* primitive ramps — there is no semantic role layer — and `aSprinkleOfCodeTheme.js` consumes primitives directly throughout (`bg-[var(--color-dark-800)]`, `text-[var(--color-primary-400)]`, `focus:ring-[var(--color-primary-400)]/30`). `src/theme/theme.css` (the Tailwind v4 `@theme` mapping AD-10 mandates) **does not exist at all**. AD-10 is therefore a change, not a ratification, yet AD-17's enumerated baseline-story scope lists only "the existing `.tsx` files + `App.jsx` / `main.jsx`" — it omits `aSprinkleOfCodeTheme.js`, the colors.css role layer, and theme.css, all three of which the Structural Seed nonetheless shows as present. The first component story cannot obey AD-10 without inventing that layer mid-story. Secondary: AD-9 says a substantively-edited file migrates on touch, so the `.js → .ts` rename of the theme object drags the *entire* flowbite theme object's token rewrite into whichever story touches it first — an unbounded scope grenade. | Add the role layer + `theme.css` + the `aSprinkleOfCodeTheme` token rewrite explicitly to AD-17's baseline-story scope list, and state that `index.css` `@import`s `theme.css` so the `@theme` block is actually processed. |
| **H-3** | high | 2, 3 | **AD-4(c)'s rule and its enforcement mechanism disagree about what gets published.** The rule says "**promoted** `mockups/`" are committed; the mechanism (`_bmad-output/.gitignore`, which excludes only `.working/` and `.memlog.md`) commits *all* of `mockups/` with no promotion gate, plus `imports/`, which neither AD-4(c) nor D-24 mentions. More consequentially, the enumerated `architecture/` scope silently publishes `architecture/reviews/*.md` — adversarial critique of the work, including this file — while byte-identical review artifacts sitting in `.working/` (`review-rubric.md`, `review-accessibility.md`, `review-rubric-prd.md`) stay private. Publication status is decided by which folder a reviewer happened to write into, which is precisely the ambiguity AD-4(c) exists to remove. Note this is a *category* question, not a taste one: D-24's rationale ("finished documents are evidence; the trail behind them stays local") argues reviews are trail. | AD-4(c) enumerates at file/folder granularity and the `.gitignore` matches it: either add `architecture/reviews/` and `imports/` to the ignore list, or amend AD-4(c) to say reviews are deliberately published as part of the evidence. Define "promoted" as a location (`mockups/` committed, drafts in `.working/`). |
| **H-4** | high | 3 | **A Deferred item can silently create the third Beyond-the-Code dimension that D-18 and AD-18 both forbid.** "Birdhouse care-guide surface (internal `personal` MDX page vs external link)" is deferred as architecture-neutral — but it is not. If it lands as `src/content/personal/birdhouse-care-guide.mdx`, AD-2 and AD-5 mechanically make it a sibling registry entry, i.e. a third card in the `/beyond` index and a third `/beyond/:slug` route. That contradicts D-18 ("exactly two dimensions, no placeholder for a third") and the very example AD-18 names as forbidden. Two builders diverge with both obeying every AD. | The Deferred row states the constraint: if internal, the care guide is reachable *from within* the making dimension's story body (a whitelisted link/block per AD-8), never a top-level `personal` registry entry. Or give `personal` frontmatter a `listed?: boolean` / `parent?: slug` so a `personal` page can exist off the dimension index. |
| **M-1** | med | 7 | **Scroll and focus behaviour across navigation is a wholly silent dimension** — and the D-21 re-set makes it matter more, not less. The primary persona now reads deeply, returns to an index, and explores a second dimension (UJ-2 step 5); that journey is *built out of* back-navigation. Under `HashRouter` + plain `<Routes>` (no data router, so no `<ScrollRestoration>`) + `React.lazy` route pages + a dynamically-imported MDX body, nothing resets scroll on forward navigation or restores it on back, and the reset must happen *after* Suspense resolves or it lands on the fallback's height. Every route page will hand-roll this differently, and where focus goes on route change is equally unowned (an a11y obligation under NFR-1 that `jsx-a11y` cannot catch). EXPERIENCE §13 only says visitors must move between paths "without relying on browser back behavior" — it does not own scroll or focus management. | One AD or Convention row: a single `useRouteTransition`-style helper in `src/lib/` owns post-navigation scroll position and focus target (skip-to-content / `<h1>` focus) for every route, resolved after Suspense; back-navigation to an index restores the prior scroll position. |
| **M-2** | med | 7 | **The client runtime / environmental envelope is undeclared.** The spine covers the ops envelope well (static hosting, no runtime, rollback = revert — the v1 R2 fix landed), but says nothing about the *client* envelope: no browser-support baseline, no `build.target`, no Node floor. This is not academic — Vite 7's default target and Tailwind v4's documented browser floor are not the same set (Tailwind v4 leans on `oklch`/`@property` and requires a notably newer Safari than Vite's default baseline), so the build will happily emit CSS that silently degrades on browsers the build target claims to support, and nobody is told which number wins. The deploy workflow pins `node-version: lts/*` — a floating version the spine ratifies by saying the workflow "runs unchanged". NFR-2 speaks only to *viewport sizes*, never to engines. | A Conventions row: named minimum browser set (take the stricter of Vite's target and Tailwind v4's floor), an explicit `build.target`, and a Node floor recorded in `engines` + the workflow. Exact version numbers belong to the web-verification lens. |
| **M-3** | med | 2, 5 | **AD-11's OPEN hover clause blocks the build without naming a legal interim move.** "A component needing it raises it as a DESIGN question — it does not pick a hex" prevents the divergence but leaves the builder of the first primary button with no way to finish the story. It also drops the escape hatch DESIGN §18a (A3) actually offers ("button labels ≥ 18.66 px / ≥ 14 px bold remain an acceptable alternative route for a specific control"), and it collides with AD-10's promise that `cssVar(name: TokenName)` returns "a documented per-token fallback" for every token — `--brand-primary-fill-hover` is a token whose value is deliberately undefined, so either it is absent from `TokenName` (and AD-10's typed helper cannot name it) or it has a fallback (and AD-11's "do not invent a value" is already violated). | AD-11 names the interim behaviour: until DESIGN answers, a primary fill's hover state changes something other than fill (border/elevation/label weight per §18a A3's alternative route), and `--brand-primary-fill-hover` is not declared in `colors.css` nor present in `TokenName`. |
| **M-4** | med | 5 | **The spine says the social handles are unknown; the deployed `index.html` already contains them.** Conventions: "Exact social handles are supplied by Alisha (PRD A-14) — do not invent," and SPEC CAP-8/CAP-9 say the link is omitted until a destination exists. | **M-5** | med | 2 | **AD-17's stated "Prevents: merges going ungated after the baseline exists" is not what its Rule achieves.** `.github/workflows/main.yml` triggers only on `push` to `main` and `workflow_dispatch` — there is no `pull_request` trigger, so the gate (`tsc && eslint && vitest && vite build`) runs *after* the merge decision, as part of deploy.
